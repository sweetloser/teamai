# 同类问题判定

## 目录

- 判定顺序
- 可直接合并的模式
- 必须拆分的模式
- 现有钉钉行选择
- 计数规则

## 判定顺序

按以下顺序建立根因指纹：

1. 去除地址、偏移、线程号、对象地址和编译器生成哈希。
2. 找到崩溃线程上的首个业务或第三方 SDK 栈帧。
3. 提取异常核心，例如 `attempt to insert nil`、`range exceeds data length`、`Could not connect to development server`。
4. 对 RN/Hermes 提取稳定的 JS 错误、TurboModule 名称或 VM/GC 函数族。
5. 组合 `模块 + 函数族 + 核心错误`，再与钉钉已有描述的历史来源比较。

同一指纹可以跨 App 版本合并；版本只作为来源分布，不作为拆分根因的默认依据。

## 可直接合并的模式

- 同一 SDK、同一崩溃函数，地址或偏移不同。
- 同一业务方法，Swift 符号因编译版本略有差异。
- RN 同一稳定错误核心，例如缺少同一个 TurboModule。
- Hermes 同一 VM/GC 函数族和同一失败类型，例如 HadesGC OOM。
- CoreBluetooth 同一入口函数和同一上层业务调用链。
- 一个已有根因组内包含零增量 Issue 与有增量 Issue；零增量来源保留在描述中但不重复累加。

## 必须拆分的模式

- 仅信号相同：`SIGSEGV`、`SIGABRT`、`SIGTRAP` 不能单独作为合并依据。
- 同一 SDK 但崩溃函数属于不同生命周期，例如定时器 resume 与字典写入。
- 同一底层 `objc_msgSend` 或 `objc_release`，但首个业务栈不同。
- RN 的不同 JS 错误、不同缺失模块、开发服务器连接失败与业务 JS 异常。
- 未符号化栈与已符号化且根因明确的栈。
- 完整详情不足以确认根因时，放入 `manualReview`。

## 现有钉钉行选择

按以下优先级选择 canonical 行：

1. 相关链接与当前 Issue ID 完全相同。
2. 详细描述的“合并来源”已包含当前 Issue ID。
3. 标题和根因指纹一致。
4. 多行都匹配时选择信息最完整且累计口径连续的一行，并把其他行列入人工核对。

不要仅凭标题中都含有 SDK 名称合并。不要在常规同步中删除历史重复行。

## 计数规则

- 钉钉新总数 = 钉钉当前累计值 + 本次 Issue 增量之和。
- 本次增量来自历史 Bugly 详情快照，不来自本周列表总数。
- 设备数按同一 Issue 的跨次增量累加；这是业务约定，不代表跨 Issue 的真实去重设备数。
- 跨版本合并时保留所有版本，按首次出现顺序去重。
- 当前值小于历史值时视为计数回退，增量为 0 并进入人工核对。
- 无本地历史且未打标签的 Issue 只是“候选新问题”。若其 Issue ID 已存在于钉钉相关链接或详细描述，必须先恢复基线或人工核对，不能直接使用当前总数。
